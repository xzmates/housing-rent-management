# 每日当前待收提醒内容优化需求

## 简介

在不更换现有微信订阅消息模板、不增加每日发送条数的前提下，提高“当前待收”微信提醒的信息准确性和可读性。完整明细仍由小程序首页承载。

## 需求

### 需求 1 - 汇总口径准确

**用户故事：** 作为房东，我希望微信提醒中的金额、待收项数和逾期笔数与首页一致，以便不打开小程序也能快速判断催收优先级。

#### 验收标准

1. 当定时任务生成提醒时，系统应继续复用 `getCurrentReceivableGroups` 的查询结果。
2. 当存在多个房屋、租客、费用类别组合时，系统应将每个组合计为一个“待收项”，不得称为“类”。
3. 当生成账单类型字段时，系统应显示主要账单类型、待收项数和逾期账单笔数，例如 `租金｜2项5笔逾期`。
4. 当计算逾期状态时，若逾期账单数等于全部未结清账单数，系统应显示 `全部逾期`。
5. 当计算逾期状态时，若逾期账单数大于零且小于全部未结清账单数，系统应显示 `部分逾期`。
6. 当不存在逾期账单时，系统应显示 `暂无逾期`。
7. 当生成截止日期时，系统应继续显示全部当前待收中的最早到期日。

### 需求 2 - 备注展示重点待收项

**用户故事：** 作为房东，我希望备注优先展示最需要处理且金额较大的待收项，以便快速识别房间、租客和金额。

#### 验收标准

1. 当排序当前待收项时，系统应先排列包含逾期账单的待收项，再在同一逾期优先级内按待收金额从高到低排列。
2. 当仅有一个待收项时，系统应按“房间简称 + 租客简称 + 金额”生成备注。
3. 当恰有两个待收项时，系统应压缩展示两个待收项，例如 `101小笛子6400；204小晶2700`。
4. 当待收项超过两个时，系统应展示排序第一项，并将其余项合并为 `另N项+其余待收总额`，例如 `101小笛子6400；另3项2700`。
5. 当房屋标签包含楼栋或地址时，系统应优先提取房间编号用于备注。
6. 当租客姓名过长时，系统应自动缩写姓名，同时优先保留房间、金额和剩余项数量。
7. 当生成备注时，系统应保证 `thing9` 的值不超过 20 个字符。

### 需求 3 - 模板格式安全

**用户故事：** 作为系统维护者，我希望发送前约束模板参数，避免因长度或格式错误产生微信错误码 `47003`。

#### 验收标准

1. 当生成 `thing18` 或 `thing9` 时，系统应保证各字段不超过 20 个字符。
2. 当生成 `phrase17` 时，系统应仅使用 `全部逾期`、`部分逾期`、`暂无逾期` 三个合法中文短语，且不超过 5 个汉字。
3. 当生成 `time37` 时，系统应使用 `YYYY年M月D日` 格式。
4. 当生成 `amount28` 时，系统应输出有效数字文本。
5. 当字段经业务压缩后仍超过限制时，系统应执行最终安全截断，不得直接发送超限参数。

### 需求 4 - 消息跳转与完整明细

**用户故事：** 作为房东，我希望从订阅消息进入可访问的小程序首页，并查看完整待收明细。

#### 验收标准

1. 当小程序尚未正式发布时，系统应使用 `developer` 跳转版本供管理员或开发成员验证。
2. 当小程序上传体验版后，系统可通过配置切换为 `trial`。
3. 当小程序正式发布后，系统可通过配置切换为 `formal`。
4. 当用户进入小程序首页时，首页应继续展示完整房屋、租客、费用类别、期间和金额；订阅消息不重复承载完整列表。
5. 当仅调整跳转版本时，系统不得硬编码 AppSecret、模板 ID 或其他密钥。
